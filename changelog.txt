*** CartShift – OpenCart to WooCommerce Migration Changelog ***

2026-06-04 - version 2.5.91
* Fixed - MULTILINGUAL now follows the SAME entity scope as the run. Previously, when the multilingual step ran it ALWAYS processed every taxonomy/post type (categories, brands, products, pages) regardless of which entities were selected — so "Products only" would still re-sync category translations, and any narrow run could rewrite category/brand slugs. New mlEntityInScope() check gates each phase by the run's per-entity flags (run_categories, run_manufacturers, run_products, run_information): a scoped run only syncs translations for the entities chosen, while a full/unscoped run still syncs everything. Term-slug auto-fix is likewise limited to taxonomies in scope. This means "Products only", "Pages only", etc. will not touch the categories you manually corrected in WooCommerce.

2026-06-04 - version 2.5.90
* Fixed - ENTITY SELECTION now strictly honoured for multilingual. Previously the multilingual/translation sync step ran whenever WPML/Polylang was enabled in Settings, regardless of which entities the user selected — so choosing "CMS Pages only" would still re-sync category (and other taxonomy) translations, touching data the user intentionally left alone. The migration config bridge now preserves an explicit run_multilingual=0 from the entity selection instead of overriding it from the global setting. Selecting specific entities without multilingual will no longer run the multilingual step.

2026-06-01 - version 2.5.89
* Fixed - MISLEADING PROGRESS TABLE: the dashboard showed per-run checkpoints for only ONE run_id, so entities migrated in earlier runs (or via CLI) displayed as "0 / — PENDING" even though thousands existed in the store. The progress endpoint now also returns live store counts (actual products, categories, brands, orders, customers, images, coupons, pages, tags that exist in WooCommerce right now, HPOS-aware). When a migrator shows pending/zero for the current run but the store actually contains that entity, the row now shows the real count with an "IN STORE" status instead of "PENDING 0". Counts are cached 30s to keep polling light.

2026-06-01 - version 2.5.88
* Fixed - RE-RUN SAFETY: the Images step previously skipped entirely once marked "complete", so re-running after adding products in OpenCart (or after some images failed to download) never picked up the new/failed images. Now a re-run re-scans when the source has more images than were processed (new products) and supports a force_images flag to re-check everything for previously-failed downloads. Per-image dedup (by OpenCart path, then MD5 hash) means already-imported images are reused instantly — never re-downloaded — so re-scans are cheap and safe. This makes the common customer workflow (periodic OpenCart updates: new products, new images) work correctly without duplicating media.
* Note - Verified ProductMigrator re-run idempotency: existing products are matched by id_map/_octowoo_oc_id (then SKU) and updated or skipped, never duplicated; a skipped product with no thumbnail still gets its image backfilled on re-run.

2026-06-01 - version 2.5.87
* Added - 'wp octowoo relink_brands' CLI command. Re-links products to their BRAND from the OpenCart source (oc_product.manufacturer_id → WC product_brand term matched by the brand's _octowoo_oc_id) without re-importing products. Links ORIGINAL products only (brands are English-only; Arabic twins inherit the brand from their original). Idempotent — appends the brand, never removes existing terms. Supports --only-missing (touch only products with no brand) and dry-run by default. Mirrors relink_categories.

2026-06-01 - version 2.5.84
* Added - MARKETPLACE RELIABILITY (Blocker 4): background cron-health detection with automatic foreground fallback. Many managed hosts silently fail the WP-Cron loopback, so background migrations "freeze at Chunk-start". New BackgroundProcessor::cronHealth() probes whether Action Scheduler's queue has actually run recently; new octowoo_cron_health AJAX action exposes it. Before starting ANY background migration (full Start in Background, Resume in Background, and the Re-run Multilingual recovery), the dashboard now checks cron health and, when it looks dead, recommends running in the browser foreground instead — which drives chunks directly over AJAX and cannot stall on cron. The user can still choose background anyway. Re-run Multilingual now runs in the foreground by default on hosts without working cron, fixing the most common "stuck migration" support case.

2026-06-01 - version 2.5.82

Before any data-changing taxonomy action (Full Reset, Full Cleanup, Fix Orphan Categories, De-duplicate Terms, Audit Purge, Fix Category Slugs) the plugin now (1) requires an explicit "I have a backup" confirmation and (2) automatically writes a JSON restore snapshot of the affected terms, term_taxonomy, product relationships, and WPML icl_translations rows to wp-content/uploads/octowoo-logs/restore/. 2026-06-01 - version 2.5.81
* Changed - MARKETPLACE: Log files now live in wp-content/uploads/octowoo-logs/ instead of inside the plugin folder. 2026-06-01 - version 2.5.78

Idempotent (skips categories that already have an Arabic twin), dry-run by default. This makes English and Arabic category counts match with proper Arabic names.

2026-06-01 - version 2.5.71
* Fixed - Category (term) translation linking now uses DIRECT icl_translations writes, exactly like the working product path (linkPostTranslation), instead of WPML's do_action('wpml_set_element_language_details') hooks. The hook path was slow (full taxonomy re-sync per term) and unreliable (re-labeled English terms as Arabic on re-runs). The direct path is deterministic and idempotent: the primary English row is created only if absent and never flipped if already correct, and the Arabic term is linked into the same trid via INSERT … ON DUPLICATE KEY UPDATE. This makes category translation behave like product translation — fast, no duplication, English stays English on re-run.

2026-05-31 - version 2.5.70
* Fixed - ROOT CAUSE of English categories being mislabeled as Arabic on every category run. The migrator relied on WPML's ambient "current language" at wp_insert_term() time to assign the language; on an Arabic-admin site (or when the language switch did not persist into the background PHP process) WPML assigned new English terms to Arabic, and re-running re-corrupted the data each time. Added ensureTermPrimaryLanguage() which writes the icl_translations row DIRECTLY in the primary language after every create/link/update, guaranteeing English terms stay English regardless of WPML's ambient context. Applied in CategoryMigrator create + term_exists + update paths.
